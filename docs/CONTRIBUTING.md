# 项目开发规范

## 1. 基本原则

- 以可读、可维护、满足当前需求为目标，避免提前抽象和无用配置。
- 优先复用已有依赖和项目能力；引入新依赖时说明用途和现有方案不能满足的原因。
- 一次变更聚焦一个目标，不夹带无关重构、依赖升级或全量格式化。
- 规范用于新代码和本次涉及的代码，已有代码随业务修改逐步调整。

## 2. 目录与命名

当前保留 `src/main.tsx`、`src/App.tsx` 和现有样式入口。随着业务增长，按需采用以下目录，不为遵守结构创建空目录：

```text
src/
  assets/       # 参与构建的静态资源
  components/   # 跨业务复用的 UI 组件
  pages/        # 路由页面及页面私有组件、hooks、样式
  hooks/        # 跨页面复用的 hooks
  services/     # Axios 请求实例及按业务拆分的接口函数
  stores/       # Zustand 客户端共享状态
  routes/       # 路由配置
  types/        # 多个业务模块共用的类型
  utils/        # 与 UI 无关的通用工具函数
```

- React 组件及文件使用 PascalCase，例如 `UserList.tsx`；hook 使用 `use` 前缀，例如 `useUserList.ts`。
- 普通变量、函数和工具文件使用 camelCase；目录使用 kebab-case；真正的全局常量使用 UPPER_SNAKE_CASE。
- 类型和接口使用 PascalCase，不使用 `I` 前缀。布尔值优先使用 `is`、`has`、`can` 等有意义的前缀。
- 业务私有代码放在所属页面或模块附近；出现实际复用后再提升到公共目录。
- 当前未配置路径别名，使用相对导入；新增别名时同步配置 TypeScript 和 Vite。

## 3. TypeScript 与代码风格

- 使用 TypeScript，React 组件使用函数组件与 Hooks。
- 遵循现有风格：两空格缩进、字符串单引号、通常不写分号，文件使用 UTF-8。基础空白规则由 `.editorconfig` 约定。
- Props、接口参数和响应结构提供明确类型；局部变量优先使用类型推导，类型导入使用 `import type`。
- 避免 `any`、无依据的类型断言和非空断言；不确定的数据使用 `unknown` 并检查后再使用。类型声明不能替代运行时校验。
- 不通过关闭检查、忽略错误或空 `catch` 掩盖问题。确需局部禁用规则时说明具体原因。
- 函数保持职责清晰，复杂条件提取为有意义的变量或函数；注释解释业务原因、边界或取舍。

## 4. React 与状态管理

- 遵守 Hooks 调用规则，列表使用稳定的业务 ID 作为 `key`，不直接修改 props 或 state。
- 组件内状态优先使用 `useState` 或 `useReducer`；跨组件共享先考虑状态提升，确有共享需要时使用 Zustand。
- 接口数据、缓存、请求状态优先由 TanStack React Query 管理，避免再复制一份到 Zustand。
- 可从 props 或 state 计算的数据直接派生；不要用 Effect 同步可计算值。Effect 用于外部系统同步，并按需清理订阅、定时器等副作用。
- 项目已启用 React Compiler，不默认添加 `useMemo`、`useCallback` 或 `memo`；仅在明确需要且有依据时使用。
- 页面负责组织业务流程，共用组件通过明确的 props 交互，避免让通用 UI 隐式依赖某个页面的 store 或接口。

## 5. 接口与异常处理

- 在 `services/` 统一管理 Axios 实例、基础地址、超时与共用错误处理，按业务拆分接口函数。
- 基础地址等环境差异通过环境变量配置，不在业务组件中硬编码；新增变量时维护脱敏的 `.env.example` 并说明用途。
- 浏览器可见的环境变量不能存放密钥。真实凭据和本地私有配置不得提交。
- React Query 的 query key 应包含影响结果的参数；数据变更成功后按需更新或失效相关缓存。
- 明确区分加载、空数据、失败与成功状态；错误提示应可理解、可操作，避免全局和页面重复提示同一个错误。
- 避免无条件重试写操作；提交期间防止重复点击。并发请求按需处理取消或过期结果覆盖问题。

## 6. UI 与样式

- 通用交互组件优先使用 Ant Design，复用一致的表单校验、反馈和交互模式。
- 组件样式优先使用 CSS Modules（`*.module.css`）；全局样式用于重置、主题变量和基础布局，现有入口样式可渐进调整。
- 颜色、间距等重复设计值优先复用主题 token 或 CSS 变量，避免散落的魔法值和滥用 `!important`。
- 使用语义化 HTML；可点击操作使用按钮或链接，表单提供标签，图标按钮提供可访问名称。
- 保留键盘操作和可见焦点，图片提供合适的替代文本；页面检查窄屏布局和内容溢出。

## 7. 验证要求

- 简单功能不需要补充单测，完成必要的静态检查和手动验证即可。
- 复杂业务规则、关键流程、数据转换和易回归缺陷，应补充适当的自动化验证，覆盖正常情况、边界和失败路径。
- 当前没有测试脚本或测试框架。确需引入时单独说明方案、依赖和运行命令，不为简单改动搭建测试体系。
- 代码提交前执行 `pnpm lint` 和 `pnpm build`；涉及页面或交互时手动验证相关流程，并检查控制台错误。
- 接口功能验证加载、空数据、请求失败和重复提交；纯文档修改检查链接、路径、命令和内容一致性。
- 区分实际通过、未执行和已有失败，不把构建通过当作完整业务验证。

## 8. Git 与协作

仓库启用 Git 后采用以下约定：

- 分支名使用 `feat/简短英文描述`、`fix/简短英文描述`、`docs/简短英文描述` 等形式。
- 提交信息使用 `type(scope): 描述`，scope 可省略；常用 type 为 `feat`、`fix`、`docs`、`refactor`、`chore`、`test`。
- 示例：`feat(user): 新增用户列表筛选`、`docs: 补充本地启动说明`。
- 提交前自查差异，不提交 `node_modules/`、`dist/`、真实凭据、临时文件或无关编辑器配置。
- 合并请求说明改动目的、主要行为变化和验证结果；界面变化附截图，存在兼容性变化时说明迁移方式。
- 修改开发命令、环境变量或目录约定时同步更新相关文档。

## 9. 完成检查

- 需求与异常路径已处理，无无关修改。
- 命名、类型、组件职责和状态归属清晰。
- 必要检查已执行，验证结果和未覆盖内容已记录。
- 配置、依赖锁文件和文档与改动保持一致。
